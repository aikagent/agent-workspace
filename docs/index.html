Clone. Set up. Work.

agent-workspace turns the projects you work on into a workspace of AI agents: one agent per project and role, each with your team's rules, the project's context and only the tools its role allows. A terminal wizard sets everything up.

Quick start

Three commands to a working workspace

Needs bun and git. The wizard installs omp if it is missing (after your yes) and recommends pass for secrets.

git clone git@github.com:aikagent/agent-workspace.git
cd agent-workspace
./setup

One question at a time, with a default for each. Most steps write through the same ./setup commands you can run by hand. Anything written outside this folder (your omp MCP config, pass entries) happens only after your yes.

Import

Bring your current setup over, untouched

Already working in a folder of projects (say ~/Code)? Answer yes at the Import step and give its path. The wizard proposes what each entry is; you adjust and confirm. The source folder is only read.

0changes to the source

Projects

Matched or new
A folder matching an org project (repo folder name or git remote) lands in projects/<org>/<project>/<repo>. Any other git repo or folder with agent files becomes a new project in your local org checkout; commit it to the org repo through its review.
Worktrees and uncommitted work
Copied as they are. A worktree living next to its repo goes next to the repo's copy, and every link is re-pointed so no copy shares a repository with the original.

Data

Everything else
Backups, exports and loose files go to data/, which git ignores. Untick anything you want left out.

Made to work in the copy

Paths and Python
Old paths in local config files the copy's git does not track (.env, settings.local.json) are re-pointed; tracked files are listed, not changed. Python environments are rebuilt with uv, the copied one kept as .copied.
Clones, not duplicates
On macOS, copies are APFS clones: instant, with no extra disk until a file changes. A repeated import copies only what is missing.
Resume and re-run

Stop any time; pick up where you left off

Progress is saved in workspace.yml after each step. Ctrl+C, a closed terminal or a failed step leaves that step to run again. Tools and sign-in are checked on every run because a login can expire.

First run

Straight through
Goes from Organisation to Finish, then offers the Main session.

Interrupted

Resume at <step>
Default choice. Or go through all steps again (keeps everything set up), or pick one step.

Finished

Change one step
Default choice: add a project, an agent, a vault, routing. Or launch the Main session.
Roles

Three levels, tighten only

A role is defined in core, can be specialised by your org (orgs/<org>/roles/) and again by a project (orgs/<org>/projects/<p>/roles/). Each level points to its parent with extends: and can only tighten: deny or prompt tools, add read-only paths and must-not rules, turn writes off, narrow MCP servers.

What the generated agent enforces on omp
  • overlay.yml: denied and prompted tools; read-only roles also deny edit, write and ast_edit.
  • The repo's own MCP config (.mcp.json and the like) is never loaded; agents get only your user-level servers.
  • role.md: org rules, code hosts, project context, must-not rules and read-only paths, as instructions.
  • On other agents, everything is instructions: open the agent in its cwd and give it role.md.
Secrets and MCP

Secrets live in pass, never in files

When the wizard adds an MCP server from another agent, every token or key becomes a reference in omp's config, and the wizard runs pass insert so you type the value straight into pass. It never sees, prints or copies the value.

With pass

Reference in omp's config
Stored at work/<org>/mcp/<server>/<key>. ./setup verify checks each reference exists, by name only.
"!pass show work/acme/mcp/tracker/Authorization"

Without pass

Environment variables, with a warning
Until pass init <gpg-id>, each value gets its own variable name and the wizard warns on every run.
TRACKER_AUTHORIZATION

Skipped

Unknown fields are not copied
A server with a field that could hold a secret (e.g. an OAuth block) is skipped with the reason; add it by hand. Blocked servers are never offered.
Provider sign-in stays with omp login, which keeps its own credentials.
Model routing

Switch provider before a limit hits

Off by default: agents use your own omp setup. Turn it on in the wizard or with ./setup routing set <role> <provider/model> ….

Subagents

A router skips a provider at 95% of its short window (e.g. 5 hours) or 80% of its weekly window; among the rest, the soonest short-window reset goes first. Change the thresholds with ./setup routing limits.

The agent's own session

Starts on your model for its role and moves down the list on a provider error or when a provider nears its limit.

Already routing?

If your omp has its own router extension or fallback chains, keep workspace routing off: both would act on every spawn.
Daily use

Start working

The Main session is your entry point; project agents are where the work happens.

Main session

Run omp in the workspace folder. It follows the workflow rules in AGENTS.md.

A project agent

Copy its launch command from agents/<org>/<project>/<role>/agent.yml (launch.omp) and run it in a terminal tab.

Keep it healthy

./setup verify after changes; ./setup → Change one step to add a project or agent; git pull for tool updates (dependencies refresh on the next run).

For team leads

Set up your org repo

Copy core/templates/org/ into a new private repo, fill it in, and share its URL with your team. Each engineer adds it in the wizard's Organisation step.

Org repo layoutprivate
